4.1 常见面试题

1Socket 编程：bind / listen / accept 各做了什么？★★★★
一句话bind 把 socket 绑定到「IP+端口」，listen 让 socket 进入监听并建立连接队列，accept 从队列里取出一条连接并返回新 socket 用于通信（原 socket 继续监听）。
展开：API 三步 & 调用流程

核心调用顺序（服务器端）

int fd = socket(AF_INET, SOCK_STREAM, 0);   // 1. 创建 TCP 套接字
bind(fd, (struct sockaddr*)&addr, sizeof addr);   // 2. 绑定本地 IP + 端口
listen(fd, backlog);                               // 3. 进入监听，设置连接队列长度
int cfd = accept(fd, &cli_addr, &cli_len);        // 4. 取出连接，返回新套接字 cfd
sequenceDiagram participant P as 进程 participant K as 内核 P->>K: socket() 创建套接字 P->>K: bind(IP, port) 绑定本地地址 P->>K: listen(backlog) 监听 + 建连接队列 K-->>P: 等待客户端 SYN... P->>K: accept() 取出一个连接 K-->>P: 返回新套接字 cfd（用于通信）

三者职责对照

函数作用关键点
bind将本地地址（IP+端口）绑定到套接字检查端口是否被占用、地址是否合法，写进内核套接字结构
listen设为监听模式，准备接收连接创建连接请求队列，backlog 决定队列最大长度，满了则拒绝/丢弃新请求
accept从队列取出一个连接，返回新 socket队列空则阻塞；原监听 socket 继续监听，新 socket 负责本次通信
2TCP 三次握手的具体过程★★★★★
一句话客户端发 SYN，服务器回 SYN+ACK，客户端再回 ACK，双方进入 ESTABLISHED。用两个序列号 Seq 与对应 Ack 完成状态同步。
展开：时序图 & 状态变化
sequenceDiagram participant C as 客户端 participant S as 服务器 Note over C,S: 初始：C=CLOSED, S=LISTEN C->>S: ① SYN (Seq=x) Note over C: 进入 SYN-SENT S->>C: ② SYN+ACK (Seq=y, Ack=x+1) Note over S: 进入 SYN-RECEIVED C->>S: ③ ACK (Ack=y+1) Note over C,S: 双方进入 ESTABLISHED，连接建立
  • 第一次：客户端发 SYN，携带自己的初始序列号 Seq=x，状态 CLOSED → SYN-SENT。
  • 第二次：服务器回 SYN+ACK，携带自己的 Seq=y，并确认 Ack=x+1，状态 LISTEN → SYN-RECEIVED。
  • 第三次：客户端发 ACK，确认 Ack=y+1，双方进入 ESTABLISHED。
3为什么需要三次握手？两次可以吗？★★★★★
一句话三次才能确认双方收发能力都对等，并防止网络延迟产生的过期 SYN 浪费服务器资源，所以两次不够。
展开：两个核心原因
  • ① 确认双方收发能力：两次握手时服务器发出 SYN+ACK 就以为连接建立，但客户端可能没收到，双方状态不同步，服务器发的数据会被丢弃。
  • ② 防止过期 SYN 浪费资源：若客户端的历史 SYN 因网络延迟迟到，服务器两次握手会误建连接占用资源；第三次 ACK 能确认客户端"确实想要连接"，避免浪费。

记忆点：三次握手 = 「双向确认」+「防历史报文」。两次只能单向确认。

4一次完整的 HTTP 请求过程★★★★★
一句话DNS 解析 → TCP 三次握手 → 发送请求 → 服务器处理 → 返回响应 → 浏览器渲染 → 关闭连接。「先解析域名，再建连接，再收发数据」。
展开：流程 & 七步图解
flowchart TD A[DNS 域名解析出 IP] --> B[TCP 三次握手建连] B --> C[发送 HTTP 请求报文] C --> D[服务器处理请求] D --> E[返回 HTTP 响应] E --> F[浏览器解析渲染] F --> G[四次挥手关闭连接]
  1. DNS 解析：域名 → IP。
  2. 建 TCP 连接：三次握手。
  3. 发请求：HTTP/HTTPS 请求报文。
  4. 服务器处理。
  5. 返回响应。
  6. 客户端解析：渲染 HTML/CSS/JS。
  7. 关闭连接：HTTP/1.1 短连接则四次挥手断开。
5TCP 和 UDP 的区别★★★★★
一句话TCP 面向连接、可靠、字节流、慢；UDP 无连接、不可靠、报文、快。可靠 vs 实时，是二者取舍核心。
展开：完整对比表
特性TCPUDP
是否连接面向连接（三次握手）无连接
可靠性可靠（确认、重传、流量控制）不保证（可能丢包/乱序）
传输方式字节流数据报
速度/开销较慢，开销大快，延迟低
头部开销≥20 字节固定 8 字节
广播/多播不支持支持
典型场景HTTP、FTP、邮件视频会议、直播、游戏、VoIP
6TCP 四大拥塞控制算法★★★
一句话慢启动指数增长探带宽，拥塞避免线性增长防拥塞，快重传靠3 个重复 ACK不等超时，快恢复窗口减半后线性恢复。
展开：四算法要点
算法目的增长/触发方式
慢启动逐步探测可用带宽从 1 MSS 起，每收 ACK 翻倍（指数），到 ssthresh 切换
拥塞避免接近拥塞时减速每 RTT 窗口 +1 MSS（线性）
快重传快速补发丢失包收到 3 个重复 ACK 立即重传，不等超时
快恢复避免退回慢启动窗口减半（降到 ssthresh）后线性增长

记忆口诀：慢启动「翻倍跑」，拥塞避免「慢慢加」，快重传「见三就重发」，快恢复「砍半再线性」。

7如何看和对端设备通不通？（Ping 原理）★★★★★
一句话Ping 基于 ICMP，发 Echo Request、收 Echo Reply，靠时间差算出 RTT，统计丢包率判断连通性。
展开：工作流程
sequenceDiagram participant S as 源主机 participant R as 目标主机 S->>R: ICMP Echo Request (序列号+时间戳) R->>S: ICMP Echo Reply (相同序列号+时间戳) Note over S: 记时间差 = RTT，统计丢包率
  • 构造 ICMP Echo Request，含目标 IP、序列号、时间戳。
  • 目标主机收到后回 ICMP Echo Reply，携带相同序列号/时间戳。
  • 源主机收到后计算往返时间 RTT，多次发送统计丢包率和平均 RTT。

4.2 区别类

8HTTPS 和 HTTP 的区别★★★
一句话HTTPS = HTTP + SSL/TLS 加密，多了加密、完整性、身份认证，默认端口 443（HTTP 为 80）。
展开：对比表
特性HTTPHTTPS
安全性明文，可被窃听/篡改SSL/TLS 加密 + 完整性 + 身份认证
端口80443
加密方式无基于 SSL/TLS
性能高，开销小略低（加解密 + 握手开销）
场景公开无隐私要求的网页支付、登录、电商等
SEO信任度低搜索引擎优先，利于排名
9HTTPS 是什么？★★★
一句话HTTPS 是 HTTP 的安全版，靠 SSL/TLS 实现机密性（防窃听）、完整性（防篡改）、身份认证（防中间人）。
展开

通过在 HTTP 上加 SSL/TLS 加密协议实现安全传输；常用于支付、登录、电商等安全要求高的场景，目前已是互联网标准通信协议。

10HTTPS / SSL-TLS 如何保证数据传输安全？★★★
一句话用非对称加密安全地交换一个对称密钥，之后用对称密钥加密数据。非对称换钥匙，对称跑数据。
展开：SSL/TLS 握手时序
sequenceDiagram participant C as 客户端 participant S as 服务器 C->>S: ① 发起 HTTPS 连接请求 S->>C: ② 返回数字证书（含公钥） Note over C: ③ 验证证书合法性，生成对称密钥 C->>S: ④ 用公钥加密对称密钥后发送 Note over S: ⑤ 用私钥解密，得到对称密钥 Note over C,S: ⑥ 双方用对称密钥加解密数据

补充概念：数字证书防伪 — 对内容做 hash 得到「摘要」，再用发送方私钥加密摘要得到「数字签名」。

11GET 和 POST 的区别★★★
一句话本质：GET 幂等（参数在 URL，用于查询），POST 非幂等（参数在 Body，用于提交/修改）。
展开：对比表
属性GETPOST
参数位置URL 中（?key=value）请求体 Body 中
可见性可见（地址栏）不可见
数据大小有限制（URL 长度约 2048）理论上无限制
安全性较低（易缓存/记录）较高（需配 HTTPS）
幂等性幂等（无副作用）非幂等（可能改资源）
是否缓存可能被缓存通常不缓存
用途查询、获取资源表单提交、上传、修改

警示：不能用 GET 做增删改——GET 幂等且在弱网会重试，重复操作会产生副作用。

12DNS 的工作原理★★★★★
一句话DNS 把域名解析为 IP，走缓存优先，缓存未命中则沿「本地 → 根 → 顶级 → 权威」逐级查询。应用层UDP
展开：解析流程
sequenceDiagram participant B as 浏览器 participant L as 本地DNS(ISP) participant R as 根域名服务器 participant T as 顶级域名服务器 participant A as 权威域名服务器 B->>L: 查询 www.example.com L->>R: 递归/迭代查询 R->>L: 返回顶级服务器地址 L->>T: 查询 T->>L: 返回权威服务器地址 L->>A: 查询 A->>L: 返回 IP L->>B: 返回解析结果 IP
  • 先查本地缓存（浏览器 → 系统 → 路由器 → ISP），命中直接返回。
  • 未命中则本地 DNS 依次问 根 → 顶级(TLD) → 权威，最终取回 IP。
  • 结果被缓存，加速后续访问。
  • 主机→本地 DNS 用递归查询；本地 DNS→根/顶级用迭代查询。
13浏览器输入 URL 后显示主页的过程★★★★★
一句话DNS 解析 → 三次握手 → 发 HTTP/HTTPS 请求 → 服务器响应 → 浏览器构建 DOM/渲染树渲染页面 → 展示。
展开：完整流程图
flowchart LR A[输入URL] --> B[DNS解析为IP] B --> C[TCP三次握手] C --> D[发起HTTP/HTTPS请求] D --> E[服务器处理并响应] E --> F[解析HTML/CSS/JS] F --> G[构建DOM树+渲染树] G --> H[渲染显示主页]

与「HTTP 请求过程」相比，这里多强调浏览器侧的解析与渲染（DOM 树 / 渲染树）环节。

14Cookie 是什么？★★
一句话Cookie 是服务器存到客户端的一小段文本（键值对），用来弥补 HTTP 无状态，如维持登录。
展开：用途 / 属性 / 局限
  • 用途：会话管理（保持登录）、个性化设置（语言/主题）、跟踪统计。
  • 核心内容：键值对 Name=Value + 属性。
  • 常用属性：
    属性含义
    Domain/Path限定作用域
    Expires/Max-Age过期时间
    Secure仅 HTTPS 传输
    HttpOnly禁止 JS 读取，防 XSS
  • 局限：单个通常 ≤4KB；有隐私/安全风险（未设 Secure/HttpOnly 时）。
15Session 的工作原理★★
一句话Session 是服务器端保存会话数据的机制，客户端只带一个 Session ID（通常存 Cookie），服务器据此找回会话。
展开：流程
  1. 用户访问，服务器生成唯一 Session ID，并在服务器端存会话数据。
  2. Session ID 返回客户端，通常存 Cookie。
  3. 后续请求自动携带 Session ID，服务器据此查找会话数据、识别用户状态。
  4. 会话有生命周期，空闲超时后销毁；数据在服务器端更安全但占用服务器资源。
16Cookie 和 Session 的区别★★★
一句话Cookie 存客户端（轻量、不安全），Session 存服务器（安全、耗资源）；常配合：Cookie 存 Session ID，Session 存会话数据。
展开：对比表
属性CookieSession
存储位置客户端（浏览器）服务器端
安全性较低（易截取/篡改）较高
数据大小约 4KB理论上无限制
生命周期可持久化（按过期时间）关闭浏览器/超时失效
服务器资源不占用占用（并发高有压力）
场景偏好、非敏感信息登录状态、敏感的临时数据

19TCP 粘包 / 拆包★★★
一句话根因是 TCP 是字节流、无消息边界：粘包=多个包粘连，拆包=一个包被拆散。解决靠定长 / 分隔符 / 长度字段 / 应用层协议。
展开：原因 & 解决

原因

  • 粘包：发送端数据小、频率高，TCP 合并发送；或接收端未按边界读。
  • 拆包：数据超过 MTU 被拆分，或经历分片，或接收端分多次到达。

解决方法

方法说明
定长数据包固定每个消息长度，不足补占位符
消息边界（分隔符）消息间插 "\r\n"、"|" 等
长度字段[消息长度字段]+[消息体]，先读长度再读数据
应用层协议用 HTTP、WebSocket 等规范
成熟框架Netty、Boost.Asio、asyncio

21MTU 和 MSS 分别是什么？★★
一句话MTU 是链路层最大传输单元（通常 1500B），MSS 是 TCP 单报文最大数据负载 = MTU − IP头 − TCP头 = 1460B。
展开：公式 
MSS = MTU − IP头(20) − TCP头(20) = 1500 − 20 − 20 = 1460 字节
  • MTU：链路层能传的最大包，防止过大导致分片，以太网默认 1500B。
  • MSS：TCP 报文中去除 IP/TCP 头后的最大数据量，三次握手时协商，避免 TCP 报文被分片。
22常见 TCP 连接状态★★
一句话连接生命周期：LISTEN → SYN_SENT/SYN_RECV → ESTABLISHED → FIN_WAIT/CLOSE_WAIT → LAST_ACK/TIME_WAIT → CLOSED。
展开：状态表
状态含义
LISTEN服务器监听，等待连接
SYN_SENT客户端已发 SYN，等响应
SYN_RECEIVED服务器收到 SYN，回 SYN+ACK，等确认
ESTABLISHED连接建立，可传输
FIN_WAIT_1主动方发 FIN，等 ACK
FIN_WAIT_2主动方收到 ACK，等对方 FIN
CLOSE_WAIT被动方收到 FIN，准备发 ACK
LAST_ACK被动方发 FIN 后，等最后 ACK
TIME_WAIT主动方等 2MSL，确保对方收到 ACK
CLOSED连接完全关闭，资源释放
23TCP 四次挥手过程★★★★
一句话主动方发 FIN → 对方回 ACK → 对方发 FIN → 主动方回 ACK，主动方进入 TIME_WAIT 等待 2MSL 后彻底关闭。
展开：时序图（客户端主动关闭）

24挥手为什么需要四次？★★★★★
一句话因为 TCP 是全双工，两个方向要分别关闭：客户端先关「发送」，服务器确认后仍可能发数据，之后服务器再关自己方向，共 4 步。
展开
  • 第①②次：客户端发 FIN 表示"我不再发数据了"，服务器回 ACK；此时客户端仍能收，服务器可能还有数据要发。
  • 第③④次：服务器发完数据后发 FIN"我也发完了"，客户端回 ACK，双方彻底关闭。

对比：握手只需 3 次因为「请求+确认」可合并；挥手因为两方向关闭常常不同步，必须分开，故 4 次。

25什么是半连接队列？★★★
一句话服务器收到 SYN 回 SYN+ACK 后、尚未收到 ACK 的未完成三次握手连接，存进半连接队列（SYN_RCVD 状态）；完成握手的进全连接队列。
展开
  • 服务器首次收 SYN 后进入 SYN_RCVD，把「部分完成」的连接放入半连接队列。
  • 完成三次握手的连接才进全连接队列。
  • 队列满则新请求被丢弃（丢包）。
  • SYN-ACK 重传：未收到 ACK 会重传，等待时间指数增长（1s、2s、4s、8s…），超过最大次数则从半连接队列删除。
262MSL 等待状态（TIME_WAIT）★★★
一句话主动关闭方发完最后 ACK 后，在 TIME_WAIT 停留 2×MSL，期间该四元组套接字不可复用。
展开
  • MSL = 报文段在网络中的最大存活时间（受 IP 的 TTL 限制）。
  • 主动关闭方停留 2 倍 MSL，以便必要时重发最后的 ACK（应对 ACK 丢失、对方重发 FIN）。
  • 期间「客户端IP+端口+服务器IP+端口」四元组被保留，结束后才能复用。
27四次挥手为什么等待 2MSL？★★★
一句话① 确保最后 ACK 被对方收到（否则对方重发 FIN）；② 让本次连接的旧报文尽数消失，防止干扰复用的新连接。
展开：三点意义
  1. 确保最后 ACK 送达：ACK 丢失对方会重发 FIN，2MSL 期间能应对重传，保证彻底关闭。
  2. 防旧分组干扰新连接：让本次所有分组（FIN/ACK）从网络中消失，不污染同端口的新连接。
  3. 给被动方时间安全关闭：主动方端口保持不可用，避免过快复用引发异常。

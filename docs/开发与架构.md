## 题库模型

自定义题库 schema：

```json
{
  "version": 1,
  "categories": [{"id": "languages", "name": "语言学习"}],
  "subjects": [{
    "id": "english-grammar",
    "name": "英语语法",
    "categoryId": "languages",
    "questions": [{
      "id": "present-perfect",
      "question": "现在完成时的结构是什么？",
      "gist": "have/has + 过去分词。",
      "answer": "主语 + have/has + 过去分词，表示与现在有关的过去事件。"
    }]
  }]
}
```

类型和专题 ID 必须为以小写字母开头的 ASCII 字母、数字、连字符，最多 64 字符。题目 ID 使用字母、数字或连字符。`gist` 可选，题干和答案必填。导入先由 LibraryModel.plan 生成预览，默认合并，未提供题目保留；选择替换仅移除涉及专题中的缺失题。内容变化默认生成重置事件，勘误可显式保留；不要为另一道题复用旧 ID。题目 ID 为小写字母/数字开头的字母、数字、连字符，最多 64 字符。可附 type、options、explanation、source；选择题需 2–8 项与字母答案，填空答案用 | 分隔。

内置题库暂时保留富文本 HTML 以避免损失表格、代码块和流程图，并按专题存入 JSON。可信内置内容与用户导入的纯文本题库分开渲染。维护内置专题应修改 `data/subjects/<id>.json`，再运行 build；未来可以逐步改为 Markdown 内容，而不影响复习算法。

运行时自定义题库存储于 `knowledge-library-v1`。复习进度导出仅含进度；完整备份（knowledge-review-backup，version:1）包含 library、progress、preferences，换设备或来源推荐完整备份。恢复分合并/替换并保存撤销快照，排除原始资料与凭据。资料提取数据库的四个 store 保持不变，新增 categoryId 字段不需要升级 schema。

模块偏好存储于 `knowledge-library-preferences-v1`，包含 `recent`（去重后最多五个）、`names`（模块 ID 对应显示名称）、`categories`（用户新建的模块）、`strategies`（模块复习策略）与 `lastUsed`（使用时间戳）。跨设备取每模块最新使用时间，排序后取五个。首次升级根据现有卡片历史推导最近使用顺序；无使用记录时不预填模块。“全部知识”始终可用，完整模块清单位于管理弹窗。新建与重命名不修改内置题库 JSON 或卡片 ID。题库导入可选择覆盖目标模块，资料提取使用自身的类型选择控件。

## 复习规则与兼容性

- 等级阈值保持 30 / 60 / 85；准确率低于 40 时，等级最高为模糊。
- 连续两次熟练或掌握才毕业，中间出现模糊 / 忘记会清零 gate。
- 模糊间隔为 1 → 3 → 7 天；忘记后立即到期并强制回顾。
- 事件合并先去重，再按真实时间排序重放，导入时间不参与排期。
- 手动“未记忆”作为重置事件参与同步，不能被旧判分覆盖。
- 访客每题保留 60 条历史并保存前置 checkpoint；登录账号的新记录保留完整历史与唯一事件 ID。旧版本已经截断的历史无法恢复。
- 默认、语言、概念、实践策略改变熟练/掌握后的间隔；事件保留策略以便历史重放。AI 请求使用题目所属模块策略，而非总览当前筛选值。
- 人工标记同样推进等级和 gate，沿用原产品行为。

旧 localStorage 名称保持不变；本次不主动清空用户进度或 IndexedDB。旧专题独立 HTML 仅作为兼容跳转入口，源码备份在 archive，后续统一维护主工作台和 data。

## AI 与数据边界

Key 读取顺序为 `DEEPSEEK_API_KEY` → `deepseek.key`。`AI_MODEL` 可覆盖默认模型，`DEEPSEEK_BASE_URL` 指定兼容 chat/completions 地址。提示词不再绑定嵌入式角色，以用户给出的标准答案和资料为评分与出题依据。

本地服务默认只监听回环地址，拒绝跨来源浏览器 AI 请求，不提供登录系统或多人权限。适合个人本机使用，若要公网或团队部署，需要单独设计鉴权、额度管理与服务端持久化。

提取生成覆盖全部已解析文本块，按最多 10 块或 24000 字符分批；失败自动重试一次，再记录失败范围供手动重试。成功结果先持久化再加入界面，存储失败仍保留该批次重试范围。去重按规范化题干，不能识别语义重复。辅助知识点每批最多 20 条；取消控制尚未完善。OCR 每文件最多 30 页；真实解析/AI 网络链路仍需人工验收。

## 交付形式选择

HTML 是界面实现方式，Electron / Tauri 是应用外壳，两者可以组合，不必重写题库与算法。

| 方式 | 对当前项目的价值 | 成本 |
|---|---|---|
| 浏览器 + 本地 Node | 已可运行，维护简单，可按需局域网访问 | 用户仍需启动服务，存储依赖浏览器来源 |
| Electron | 内置 Chromium 与 Node，能复用当前 JS 后端，适合先做 Windows 桌面版 | 需新增主进程、打包、独立数据目录与更新策略，安装包通常较大 |
| Tauri | 使用系统 WebView，适合关注体积的桌面应用 | 需 Rust 工具链和平台适配；现有 Node 后端需 sidecar 或改写 |

建议当前先使用模块化 Web 版本；确认独立桌面窗口与安装包需求后优先 Electron。之后的数据应迁移到固定应用数据目录，避免随机服务端口产生多份浏览器进度。

参考：[Electron 官方介绍](https://www.electronjs.org/docs/latest/)、[Tauri 进程模型](https://v2.tauri.app/concept/process-model/)、[Tauri WebView 版本](https://v2.tauri.app/reference/webview-versions/)。

## 云同步与页面刷新

KnowledgeStorage 为访客及登录账号提供隔离的三类数据；CloudModel 按专题/题目/字段做三方合并，进度按事件合并。CloudSync 用 Supabase 版本比较原子保存，冲突需用户选择。编辑或自测打开时暂缓结构更新，安全时 Library.refresh 更新发生变化的自定义专题，避免丢草稿。

PWA Service Worker 只缓存公共应用资源，不缓存 API、Supabase 响应与原始文件。缓存号由构建资源哈希生成，无需手改；应用版本更新与云端内容应用为不同按钮。修改数据 schema 时必须另行设计迁移，VERSION 的发布号不代替 schema。
